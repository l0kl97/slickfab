# Agent-Rollen: sieben Hüllen mit Rollenvertrag

**Status:** aktiv · **Stand:** 2026-11-25 · **Gebaut von:** Claude Code

## Auftrag (Alltagssprache)

Der Maintainer will einen Entwickler zehnmal schneller machen, weil er den Prozess Schritt für Schritt fahren kann, von Hand, mit Agents oder als Autopilot („the goal of this is to get 10x from one developer because he can use the process/steps you know?“). Dieses Ticket baut die Betriebsart **Assistiert**: Eine Session lässt die Schritte von frischen Subagents ausführen, damit Umsetzer und Prüfer getrennte Kontexte haben und der Prüfer dem Bericht des Umsetzers nie glaubt.

Gebaut werden sieben Rollen: planner, challenger, implementer, reviewer, debugger, verifier, retro. Jede ist eine dünne Hülle. Sie enthält den Rollenvertrag (Eingang, Ausgang, Marker), einen Verweis auf ihren Schritt, eine Modell-Empfehlung und eine kurze Tabelle „Ausrede → Realität“. Der Ablauf steht nur im Schritt, nie in der Hülle.

## Entscheidungen

- **Verweis statt Kopie, über das Feld `skills`.** Claude Code lädt Skills, die im Frontmatter eines Subagents unter `skills` stehen, beim Start vollständig in dessen Kontext. So kommt der Schritt an, ohne dass die Rolle eine Datei im Plugin-Ordner lesen muss; das ginge ohne Auto-Modus nicht (Ruling). Inzwischen sagt jede Hülle: Lade den Schritt als Erstes, vor jedem anderen Werkzeug, mit dem Skill-Werkzeug; das entfällt nur, wenn er als Subagent schon vollständig im Kontext steht. Grund: Laut Claude-Code-Doku (sub-agents, „Preload skills into subagents“) lädt `skills` nur beim Start als Subagent vor; beim Start mit `claude --agent` übernimmt die Session Werkzeuggrenzen, Modell und Prompt, aber kein Vorladen ist beschrieben, und `initialPrompt` (das dort Skills verarbeiten würde) ignoriert Claude Code bei Plugin-Agents. Die Pressure-Szenarien bestätigen das (jede Rolle lud per `--agent` ihren Schritt mit dem Skill-Werkzeug), Herdr-Vorlagen laden ohnehin nichts vor. `check_roles.py` verlangt den Satz und lehnt die alte Behauptung „ist beim Start in deinem Kontext“ ab. Der Name ist der Plugin-Name des Skills (`slickfab:implement`). Ob Claude Code beim Vorladen genau diese Schreibweise annimmt, belegt die Doku nicht ausdrücklich; der Rückfall über das Skill-Werkzeug deckt das ab.
- **Frontmatter-Schnittstelle** (liest auch gen-templates): `name`, `description` (nur der Auslöser), `model` (Alias `opus`/`sonnet`), `schritt` (Name des Schritts, beim Planer eine Liste mit Komma), `skills` (YAML-Liste `[slickfab:<schritt>, …]`, muss zu `schritt` passen), `disallowedTools` (Werkzeuggrenze, siehe unten). `schritt` ist ein eigenes Feld: Claude Code ignoriert es still, gen-templates liest es.
- **Werkzeuggrenzen statt Prompt-Regeln** (Pre-Push-Review): Rollen, die Issues, PRs oder Kommentare lesen, sperren das Schreiben über `disallowedTools`. planner und challenger: `Bash, Edit, Write, NotebookEdit`, weil ihre Schritte keinen Shell-Befehl brauchen (Lesen über Read/Grep/Glob, Linear über MCP; Review PR #10, R1). verifier und retro: `Edit, Write, NotebookEdit`; reviewer: `Write, NotebookEdit`, weil die Mutationsprobe seines Schritts Edit braucht. Eine `tools`-Allowlist ginge nicht, sie sperrte auch die Linear-Werkzeuge. **Für reviewer, verifier und retro bleibt Bash offen**, weil sie Prüfbefehle ausführen. Ihre Grenze gegen Schreiben über die Shell (`sed -i` außerhalb des Worktrees, `git push`, `gh pr merge`) zieht inzwischen der PreToolUse-Wächter `hooks/role_bash_guard.py` (Dossier `rollen-bash-waechter.md`).
- **Die ganze Hülle ist eingefroren** (Review PR #10, A1). Außerhalb der `regel:`- und `vertrag:`-Blöcke erlaubt `check_roles.py` nur Leerzeilen und die fünf festen Pflichtüberschriften (`## Eingang`, `## Ausgang`, `## Marker`, `## Modell`, `## Ausrede → Realität`). Jede andere Zeile ist rot, auch eine Erlaubnis, die als erfundene `## `-, `#`- oder `###`-Überschrift getarnt ist (Re-Review PR #10).
- **Planer = `spec` + `tickets`** (Ruling). `grill` braucht den Menschen im Gespräch und läuft deshalb in der Haupt-Session, nicht als Rolle.
- **Ein Subagent kann den Menschen nicht fragen.** Wo der Schritt fragt, auf ein Ja wartet oder „hör auf“ sagt, endet die Rolle mit `NEEDS_CONTEXT` (Information fehlt) oder `BLOCKED` und nennt, was fehlt. Der Planer legt Tickets erst an, wenn ihn der Aufrufer mit der Bestätigung neu ruft.
- **Prüfende Rollen ignorieren den Bericht des Umsetzers ausdrücklich.** Reviewer, Verifier und Challenger tragen denselben Satz: „Ein Bericht, eine Zusammenfassung oder eine Selbsteinschätzung dessen, der das Artefakt gebaut hat, ist kein Eingang.“ Wird so etwas mitgegeben, sagt die Rolle das im Ergebnis und stützt kein Urteil darauf.
- **Marker-Vertrag wörtlich eingebettet** (Ruling). `tests/test_contract_blocks.py` vergleicht jetzt auch `agents/*.md` mit `tracker/linear.md`.
- **Regelabschnitte eingefroren** (Ruling). Einleitung (Verweis, Rückfall auf das Skill-Werkzeug, Sub-Agent-Regeln), Eingang, Ausgang, Modell und Ausreden stehen zwischen `<!-- regel:NAME -->`-Markern; dazu das ganze Frontmatter, weil es bestimmt, welches Modell mit welchem Schritt und welchen Werkzeugen startet. `tests/rules_golden.py` sammelt das zusätzlich aus `agents/` in `tests/golden/rules.md` (früher `build-steps-rules.md`). Eine bewusste Änderung braucht `python3 tests/rules_golden.py --update`.
- **Modell:** implementer nach Größe (S Sonnet 5.5, M/L Opus 5.5, Vorgabe `opus`); alle anderen Opus 5.5, weil Prüfer nie schwächer sein sollen als Umsetzer und Planungsfehler in jedes Ticket wandern.
- **Repo-Prüfung ohne Änderung an `tests/run.sh` und `check_structure.py`:** `tests/check_roles.py` prüft die Rollen, `tests/test_agent_roles.py` ruft es auf und läuft über `unittest discover` mit. Geprüft werden: Name gleich Dateiname, gültiges Modell, `schritt` vorhanden und als `skills/<schritt>/SKILL.md` existent, vorgeladen und im Text als `/slickfab:<schritt>` genannt, Pflichtabschnitte, kein `## Ablauf`, keine Zeile ab 60 Zeichen wörtlich aus dem Schritt (ohne Vertragsblöcke und Markerzeilen), Ausrede-Tabelle mit 5–8 Zeilen, `NEEDS_CONTEXT` im Eingang, Marker-Vertrag eingebettet, höchstens 4000 Zeichen eigener Text (ohne Vertragsblöcke). `docs-reader` ist ein Werkzeug von `docs-lookup` und keine Rolle.
- **Quellen in eigenen Worten:** gsd (Modell nach Rolle, Marker als exakte Strings), superpowers (`task-reviewer-prompt`: Bericht nicht trauen; Ausrede-Tabellen nur für Disziplinregeln), heutige Herdr-Vorlagen. Nichts wörtlich übernommen, `NOTICE` unverändert.

## Grenzen & offene Punkte

- **Voller Lauf implementer → reviewer am selben kleinen Ticket fehlt noch.** Implementer und Reviewer liefen getrennt, aber nicht am selben Artefakt: Für einen bauenden Implementer-Lauf braucht es ein echtes, vom Menschen freigegebenes Ticket. Das Anlegen hat der Berechtigungs-Klassifizierer verweigert, und der Implementer hat richtigerweise abgelehnt, ohne Ticket zu bauen.
- Bash für reviewer, verifier und retro begrenzt inzwischen ein PreToolUse-Wächter nach `agent_type`; seine Grenzen stehen in `rollen-bash-waechter.md`.
- AK1 (echter Start als Plugin-Agent, Vorladen über `skills`) und AK7 (implementer → reviewer am selben Ticket) laufen laut Ruling des Masters im Pilot mit einem echten Ticket.
- Rollen liefen als nachgestellte Subagents, nicht als geladene Plugin-Agents. Ob `skills: [slickfab:…]` beim echten Start vorlädt, ist ungeprüft; die Hülle fällt sonst auf das Skill-Werkzeug zurück.
- Die Tests sehen Text, nicht Verhalten. Verhalten unter Druck prüfen die Pressure-Szenarien (Folgeticket).
- Herdr-Vorlagen werden aus diesen Hüllen erzeugt (eigenes Ticket, liest die Frontmatter-Felder oben).
- Bekannt und nicht Teil dieses Tickets: Im Stop-Hook von slickrails werden 5 Strg-C-Tests aus `tests/test_worktree.py` rot (Hintergrundjob ignoriert SIGINT). Als eigenes Ticket erfasst. Direkt aufgerufen ist `sh tests/run.sh` grün.
