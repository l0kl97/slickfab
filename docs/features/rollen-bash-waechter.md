# Bash-Wächter für prüfende Rollen

**Status:** aktiv · **Stand:** 2026-11-25 · **Gebaut von:** Claude Code

## Auftrag (Alltagssprache)

Reviewer, Verifier und Retro brauchen Bash, um Tests und Mutationsproben laufen zu lassen. Mit offenem Bash ist ihr `disallowedTools: Edit, Write` aber wirkungslos: Über `sed -i`, `git commit` oder `git push` könnten sie trotzdem ändern. Gefunden im Review von PR #10 (Befund R1). Gebaut wird ein PreToolUse-Wächter nach dem Muster von `hooks/docs_lookup_guard.py`. Er greift nur bei diesen drei Rollen und verweigert Bash-Befehle, die das Repo außerhalb einer Mutationsprobe dauerhaft ändern oder etwas nach außen schicken: push, commit, merge, `gh pr merge`, Schreiben außerhalb des Worktrees. Er verweigert im Zweifel und stört nie eine andere Session.

## Entscheidungen

- **Rolle über `agent_type`.** Laut Hook-Doku melden Plugin-Subagents den plugin-scoped Namen (`slickfab:reviewer`). Der Wächter vergleicht exakt mit `slickfab:reviewer`, `slickfab:verifier`, `slickfab:retro`. Alles andere (Hauptsession, Umsetzer, `reviewer` ohne Plugin-Präfix, kaputte Typen) bekommt keine Entscheidung.
- **Fail-closed nur innerhalb der Rollen.** In den drei Rollen wird jede Ausnahme, jeder unlesbare Befehl und ein unbekannter Worktree (`CLAUDE_PROJECT_DIR` fehlt, `cwd` außerhalb) zu `deny`. Ausgang immer Exit 0 mit JSON `permissionDecision: deny`, wie in der Doku für PreToolUse beschrieben.
- **Gemeinsamer Starter statt `|| true`** (Rework 1, Entscheidung des Masters). Beide Wächter (`role_bash_guard.py`, `docs_lookup_guard.py`) starten über `hooks/guard_start.py`. Der Code steht inline in `hooks.json` (`python3 -c '…' <wächter> <rollen> || true`), damit der Starter selbst nie fehlen kann. Er liest die Rolle ohne Ausnahmerisiko. Außerhalb der Rolle endet er sofort mit Exit 0, ohne den Wächter zu laden. In der Rolle startet er den Wächter per `runpy` mit 8 s Frist (unter dem Hook-Timeout von 10 s) und gibt bei fehlender Datei, Absturz, Exit ≠ 0 oder Fristablauf `deny` aus. `|| true` bleibt nur für den Fall, dass `python3` fehlt. Kein `onFailure: block`: Das würde bei einem kaputten Plugin jede Session sperren. Ein Test hält fest, dass beide Einträge genau den Code aus `guard_start.py` tragen.
- **Allowlist statt Sperrliste** (Rework 1, Entscheidung des Masters). Die Sperrliste blieb offen: zsh-Vorbefehle (`noglob`, `nocorrect`, `-`, `repeat`), Programm-Starter (`caffeinate`, `script`, `xcrun`, `npx -c`, `sqlite3 .system` …) und Schreibwerkzeuge (`xz`, `openssl -out` …) gingen durch (Review PR #15, A1). Jetzt muss das erste Wort jedes Teilbefehls genau einer dieser Namen sein, ohne Pfad:
  - Lesewerkzeuge: `cat`, `ls`, `grep`, `rg` (ohne `--pre`), `sed` (ohne `-i`, ohne Skriptdatei, nur `s`, `d`, `p`, `q`, `n`, `=`), `head`, `tail`, `wc`, `diff`, `find` (ohne `-exec`/`-delete`/`-fprint`), `sort` und `uniq` (ohne Ausgabedatei; Ausgabe nur per Umleitung), `cut`, `tr`, `jq`, `stat`, `file`, `pwd`, `echo`, `printf`, `test`, `[`.
  - `git` und `gh` mit den Unterbefehlen unten.
  - `sh`/`bash`/`node` nur mit Skript im Worktree; `python3` mit Skript im Worktree, `-m unittest|pytest|doctest` oder `-m <modul>` für ein Modul, das als Datei im Worktree liegt (siehe unten); `pytest`; `npm test`. Alle Pfadargumente müssen im Worktree liegen: jedes Positionsargument im Ganzen (also auch der Wert nach `--junitxml`), der angehängte Wert kurzer Optionen und **jeder** Teil hinter **jedem** `=` (`-o log_file=/x=1` enthält `/x=1`).
  - Prüfbefehle des Projekts, wörtlich aus `.slickrails/config.sh`, sonst `.slickfab/config` (nur `CHECK_*`, ohne Variablen und Umleitung, als Text gelesen, tolerant bei kaputter Kodierung). Sie schalten nur Programme ohne eigene Regel frei (`make test`, `npm run typecheck`). `sh -c …` oder `python3 -c …` als `CHECK_*` bleibt gesperrt, weil ein PR die Konfiguration ändern kann.
  - Alles andere wird abgelehnt. Die Mutationsprobe macht der Reviewer mit Edit; `sed -i`, `rm`, `cp` usw. sind nicht mehr erlaubt.
  - Bei `sort`, `uniq` und `sed` sind die Optionen selbst eine Allowlist (Pre-Push-Review zu Rework 1): getopt_long nimmt gebündelte Kurzschalter (`-ro ~/.zshrc`) und abgekürzte lange Namen (`--out=`, `--in`) an. Erlaubt sind nur bekannte Schalter, lange Namen nur ausgeschrieben. Optionen nur vor dem ersten Positionsargument: BSD-getopt (macOS) hört dort auf, GNU sortiert um; sonst läse `sed -n 'w ~/.zshrc' -e p` unter macOS das erste Wort als Skript. Bei git zählt jeder Anfang eines gefährlichen Namens wie der Name selbst (`--outp=`, `--upload-p=`), weil git eindeutige Abkürzungen annimmt.
- **Kein Zeilenumbruch und kein `#` außerhalb von Anführungszeichen** (Rework 1, A1.1). Ein Kommentar endet am Zeilenende. Ein `'` darin hatte die Zerlegung verschoben: `ls # '⏎git push⏎# '` las der Wächter als ein Argument von `ls`, die Shell führte Zeile 2 aus. Die frühere Entscheidung „Kommentare sind erlaubt, der Wächter sieht nie weniger als die Shell“ war falsch. Ein `\` vor Zeilenumbruch oder `#` ist ebenfalls gesperrt.
- **Nur `cd`, und nur als bloßes Wort** (Rework 1, A1.2/A1.4). `/usr/bin/cd` ist ein externes Programm ohne Wirkung auf die Shell, `chdir` (zsh) und `pushd` ändern das Verzeichnis wie `cd`. Mitverfolgt wird nur `cd` mit Ziel im Worktree; `chdir`, `pushd` und `/usr/bin/cd` sind gesperrt.
- **Selbst zerlegen statt raten.** Der Wächter zerlegt den Befehl wie die Shell (Anführungszeichen, Backslash, `;`, `&&`, `||`, `|`, `&`, Umleitungen). Abgelehnt wird, was er nicht sicher versteht: `$` und Backticks (Variablen, Ersetzung), Klammern und `{}` (Subshell, Klammerexpansion), Heredoc, Here-String, Prozessersetzung, `=` am Wortanfang (zsh), Tilde mitten in einer Zuweisung, Steuerzeichen.
- **git und gh per Allowlist.** git: lesende Unterbefehle (`status`, `diff`, `log`, `show`, `fetch`, `rev-parse` …), `worktree list|prune|add|remove` mit Pfad im Worktree, `checkout [<commit>] -- <dateien>` mit Dateien im Worktree, `branch`/`config`/`remote` nur lesend. Globale Optionen nur `-C <pfad im Worktree>`, `--no-pager`. Optionen, die schreiben oder Programme starten (`--output`, `--upload-pack`, `--ext-diff` …), sind gesperrt. `fetch`/`ls-remote` nur mit benanntem Remote. gh: `pr view|diff|checks|list|status`, `issue view|list`, `repo view`, `run view|list`, `search`, `pr review` nur mit genau `-c`/`--comment` und ohne Freigabe (auch nicht `--approve=true`), `pr comment` ohne `-R`, ohne PR-URL und ohne `--edit-last`/`--delete-last` (vorhandene Kommentare bleiben unangetastet), `--body-file` aus dem Worktree, `api` nur GET ohne Felder, `--input` und `--hostname`.
- **Schreiben nur im Worktree, nie unter `.git`.** Umleitungen und Schreibziele müssen nach `realpath` im Worktree der Session liegen (`CLAUDE_PROJECT_DIR`), nicht unter einem `.git`-Ordner. `cd` darf nur am Anfang oder nach `&&`/`;` stehen, nur vor `&&` oder am Ende, nur in einen vorhandenen Ordner, danach kein `||` (Security-Review). Platzhalter sind nur bei reinen Lesewerkzeugen erlaubt (`cat`, `ls`, `grep` …), bei git erst nach `--`. Sonst könnten sie zu einer Option oder einem Unterbefehl expandieren, wenn der PR passende Dateinamen mitbringt. zsh-Umleitungen `>!`, `>>!`, `&>!` werden wie `>|` geprüft.
- **`python3 -m <modul>` aus dem Worktree, `cd` in den gerade angelegten Prüf-Worktree** (Befunde aus den Pressure-Szenarien V1/V2 und R2). Der Verifier konnte den CLI-Befehl aus der Spec (`python3 -m reports.cli`) nicht ausführen, und `git worktree add … && cd …` scheiterte, weil der Ordner zur Prüfzeit noch nicht existiert. Gelockert ist nur so weit, wie diese Prüfungen es brauchen:
  - `-m` mit einem Modul, das als Datei im Arbeitsverzeichnis liegt. Der Wächter löst den Namen auf wie Pythons `FileFinder` (Review PR #22, A1): Auf jeder Stufe darf es genau einen Kandidaten geben (Paketordner, `<name>.py`, Bytecode oder Erweiterungsmodul), sonst ist unklar, was Python nimmt, und er lehnt ab. Jede Paketebene ist ein echter Ordner mit echter `__init__.py`, am Ende `<name>.py` oder ein Paket mit `__main__.py`. Kein Eintrag auf dem Weg ist ein Symlink, auch `__pycache__` und keine Datei darin (Python lädt eine `.pyc` mit Unchecked-Hash ohne Abgleich mit der Quelle; ein unlesbarer `__pycache__` wird abgelehnt), und jede Datei, die Python ausführt (jede `__init__.py`, Modul bzw. `__main__.py`), liegt nach `realpath` im Worktree. Namen gelten nur in genau dieser Schreibweise (macOS ignoriert Groß/klein, Python nicht), `PYTHONCASEOK` ist gesperrt. Das ist so viel wie `python3 <skript im Worktree>`, das schon erlaubt war. Abgelehnt bleibt jedes Modul, dessen oberster Name zur Standardbibliothek gehört oder eingebaut bzw. eingefroren ist (die gewinnen vor dem Arbeitsverzeichnis, `json.tool`, `site`, `os`, `http.server`, `pip`), ein Namespace-Ordner ohne `__init__.py` (verlöre gegen ein gleichnamiges installiertes Paket), `-I` und `PYTHONSAFEPATH` (nehmen das Arbeitsverzeichnis aus dem Suchpfad). Pfade hinter dem Modul prüft der Wächter wie bei Skripten.
  - `cd` in einen Pfad, den `git worktree add` **im selben Befehl davor** anlegt. Die übrigen `cd`-Regeln gelten weiter (nur nach `&&`/`;`, danach nur `&&`, kein `||`), scheitert das Anlegen, scheitert also auch `cd` und der Rest läuft nicht. `mkdir` bleibt gesperrt.
  - **Kein Schreibziel im gerade angelegten Worktree** (Security-Review). Zur Prüfzeit gibt es dessen Dateien nicht; ein Symlink aus dem geprüften Commit (`z -> ~/.zshrc`) bliebe für `realpath` unsichtbar. Im selben Befehl sind dort deshalb keine Umleitungen, kein `git checkout -- <datei>` und keine Optionswerte (`--junitxml out.xml`, `-o log_file=…`, `-Xdatei`, das Wort direkt nach einer langen Option; nach einer Kurzoption wie `-s tests` nicht, das war im Pressure-Nachlauf R2 ein Fehlalarm) erlaubt, auch nicht, wenn der Ordner schon leer existierte. Verglichen wird ohne Groß/klein und Unicode-Normalform (`.SLICKFAB-VERIFY-7/z`, `pru\u0308f` statt `prüf`), weil macOS beides nicht unterscheidet und `realpath` nicht vorhandene Pfade nicht angleicht (Pre-Push-Review). Lesen und Ausführen (`sh tests/run.sh`, `python3 -m pytest tests/x.py`) bleibt erlaubt; Schreiben geht im nächsten Befehl, dann sieht `realpath` die Dateien. Das schließt nebenbei einen schon vorher offenen Weg: `git worktree add … && printf a > <neuer Worktree>/z`.
  - **Ruling: `python3 -c` bleibt gesperrt.** Inline-Code lässt sich nicht abgrenzen; `python3 -c 'import os; os.system("git push")'` ist genau der direkte Weg, den der Wächter sperren soll. Echte Prüfungen kommen ohne aus: ein Modul oder Skript im Repo, `-m unittest|pytest`, oder ein Prüfskript, das die Rolle mit `printf … > probe.py` im Worktree ablegt und startet (die bekannte Restlücke unter Grenzen, kein neuer Weg). Kosten, falls falsch: eine Rolle braucht für Einzeiler einen Umweg über eine Datei.
- **Nur Bash.** Edit, Read usw. beurteilt der Wächter nicht; die Werkzeuggrenzen dafür stehen in den Hüllen (`disallowedTools`).

## Grenzen & offene Punkte

- **Der Wächter ist kein Sandkasten, und gegen eine gezielt gesteuerte Rolle hält er nicht** (Pre-Push-Review, Befund 1). Die Rolle darf im Worktree schreiben (Mutationsprobe, beim Reviewer auch Edit) und Skripte aus dem Worktree starten (Prüfbefehle). Zusammen ergibt das beliebigen Code: `printf 'git push …' > t.sh; sh t.sh` oder eine Zeile `git push` in `tests/run.sh` und dann die Suite. Ebenso kann ein bösartiger Test im geprüften PR selbst pushen. Der Wächter sperrt die **direkten** Wege (ein irrtümliches oder eingeschleustes `git push`, `gh pr merge`, Schreiben nach außen in einem Befehl). Eine echte Grenze bräuchte etwas außerhalb der Shell-Zeile: Rolle ohne Push-Rechte (eigenes Token nur zum Lesen und Kommentieren, Branch-Schutz auf main) oder einen Sandkasten. **Offene Entscheidung für den Menschen.**
- **Prüfbefehle und Repo-Skripte führen fremden Code aus.** `make test`, `npm test` oder `sh tests/run.sh` laufen, was im Repo steht; ändert der PR Makefile, `package.json` oder die Konfiguration, gehört das zur Restlücke oben.
- **`.githooks` liegt im Worktree** (Review PR #15, A2). In diesem Repo ist `core.hooksPath = .githooks`. Eine geschriebene `.githooks/post-checkout` liefe auch beim erlaubten `git checkout <commit> -- <datei>` und bei `git worktree add`. Das gehört in dieselbe Kategorie wie die Restlücke oben; der Schutz „nie unter `.git`“ greift hier nicht.
- **Kommentare können Inhalte tragen.** Ein Kommentar am eigenen PR bleibt erlaubt, weil der Schritt ihn verlangt. Was darin steht, prüft der Wächter nicht: Eine Rolle könnte eine Datei aus dem Worktree oder stdin (`-F -`) posten.
- **Symlinks, die erst im selben Befehl entstehen**, sieht `realpath` zur Prüfzeit noch nicht (etwa `git checkout <commit> -- link && cp x link/y`).
- **Fehlt `python3` ganz, ist die Rolle ungeschützt** (`|| true` am Starter, siehe oben). Fehlt nur der Wächter, lehnt der Starter ab.
- **Bericht-Datei:** Heredoc und Zeilenumbrüche außerhalb von Anführungszeichen sind gesperrt. Den Bericht schreibt die Rolle mit `gh pr review <PR> --comment --body "…"` (Zeilenumbrüche im Text in Anführungszeichen sind erlaubt) oder über `printf '…' > .slickfab-review-<PR>.md` im Worktree und `--body-file`.
- **Erledigt:** review Schritt 7 nennt für die Mutationsprobe nur noch Edit oder ein python3-Skript im Worktree; ein Test schickt die Befehle durch diesen Wächter.
- **Folgearbeit an `skills/review` (nicht in diesem Ticket, parallel lief ein anderes Ticket):** Der Schritt nennt `gh pr review … --body-file …`, aber nicht, wie die Datei ohne Write und ohne Heredoc entsteht. Ein Satz dazu im Schritt würde einen abgelehnten ersten Versuch sparen.
- **Folgearbeit Edit beim Reviewer:** Der Reviewer behält Edit für die Mutationsprobe. Edit außerhalb des Worktrees prüft der Wächter nicht (nur Bash); dort greifen die Rechte der Session.
- Nicht live als geladener Plugin-Agent geprobt (Auftrag: keine weiteren Agents). Belegt sind Format und Feldnamen aus der Hook-Doku und der registrierte Befehl per `sh -c`.
